# vibe-projectmanager —— 需求交付链路

一条需求从成文 PRD 走到复盘，中间每一段的产物都是下一段的输入。本 skill 管三件事：
**按顺序走**、**PRD 没过门禁不往下走**、**每段只用上一段留下的证据，不编**。

## 1 链路总图

| # | 阶段 | 输入 | 产物 | 规程 |
|---|---|---|---|---|
| 1 | 写 PRD | BRD / 口头诉求 | 成文 PRD | 交 [vibe-designing] 套件（访谈 → 体检 → describe → … → uiux） |
| 2 | 评审 PRD | 成文 PRD（冻结版本） | `评审报告-周期<c>-第<n>轮.md` + `门禁记录.md` | `references/prd-review-gate.md`；md5 用 `scripts/prd_md5.py` |
| ⛔ | **门禁** | 评审结论 + 用户确认 | 放行 / 未放行（评审结论为升级的，交用户裁定） | 同上 |
| 3 | 拆任务 | 已放行 PRD | `任务台账.md`（任务列） | `references/breakdown-and-estimate.md` |
| 4 | 估算 | 任务台账 | 台账补「估算 / 置信度」列 | 同上 |
| 5 | 识别风险 | PRD + 台账 + 门禁遗留项 | `RAID日志.md`（风险 / 假设 / 问题 / 依赖） | `references/risk-and-priority.md` |
| 6 | 排优先级 | 台账 + RAID 日志 | 台账补「得分 / 排名 / 关键路径」列 | 同上 |
| 7 | 建工单 | 排好序的台账 + 用户在当前这条消息里的明确授权 | 工单，台账补「工单号」列 | `references/tickets.md` |
| 8 | 规划 Sprint | 台账 + 本 Sprint 可用人天 + 历史完成区间 | `Sprint-<n>-计划.md`，台账补「Sprint」列 | `references/sprint-status-retro.md` |
| 9 | 状态汇报 | Sprint 计划 + 工单实际状态 + RAID 日志 | `状态汇报-<YYYY-MM-DD>.md`；转红时附升级 | 同上 |
| 10 | 复盘 | Sprint 计划 vs 实际 + 团队反馈 | `Sprint-<n>-复盘.md` | 同上 |

> 9、10 两段按 Sprint 循环；复盘的行动项和实际完成量回流到下一个 Sprint 的 5、8（见第 5 节）。
> 上线前后的业务验收不在本链路内，交 [vibe-designing-acceptance]；它的结论可以作为状态汇报和发布关卡的输入。

**项目级工件**（不属于某一段，按需建立，规程见 `references/governance.md`）：

| 工件 | 什么时候建 | 和链路的关系 |
|---|---|---|
| 章程 + 启动清单 | 跨团队、有发布节点或有发起人的项目，开工前 | 定成功指标、负责人、RAG 口径、决策权；PRD 的需求目标应能对上章程指标 |
| 干系人地图 / RACI / 沟通计划 | 随章程 | 决定第 9 段发给谁、多久一次、写多细 |
| 决策日志（ADR） | 难以撤回、影响多团队的决定出现时 | 门禁升级的裁定、范围取舍、技术选型的结论落在这里 |
| 变更请求（CR） | 要动基线（章程范围、已放行 PRD、里程碑、预算、冻结的依赖约定）时 | 批准后触发 PRD 变更评审和台账 `待重估` |
| 发布关卡 | 有对外发布的项目，每次发布一次 | 判能不能上线；接在若干个 Sprint 之后，单条小需求随所在版本的发布关卡一起过，不单独做 |
| 阶段评审 | 章程或组合约定里定好的里程碑上 | 判下一阶段要不要继续投入：继续 / 有条件继续 / 暂停 / 返工 / 停止；门槛事先写好，拍板人只有一个 |

**组合层**（两条以上需求或项目同时在跑，且共用人、彼此有依赖或要统一汇报时建，规程见 `references/portfolio.md`）：组合约定、组合台账、资源分配表、组合 RAID 日志、依赖图、阶段评审与再分配记录、组合汇报。组合层只汇总成员的产物，颜色只抄成员自报，并记录只在组合层才有的东西；成员的台账和 RAID 日志仍是唯一真源。汇总用 `scripts/portfolio_rollup.py`。

## 2 门禁铁律（PRD 通过才放行）

**放行状态**的唯一判定：`门禁记录.md` **最新一节**（评审轮、变更评审或豁免）的「门禁」栏，取值为 `放行`、`用户裁定放行`、`用户豁免`、`撤回恢复放行` 四者之一。其他取值、没有记录、或下面第 2 条的比对不一致，都算未放行。

1. ⛔ **第 3～8 段开工前先核对放行状态**，不是放行就停下，回到第 2 段。不替用户跳过门禁。
2. ⛔ **第 3～8 段开工前比对 PRD 版本**：按 `references/prd-review-gate.md` 第 1 节，用本 skill 自带的 `scripts/prd_md5.py` 重算当前 PRD 的 md5（云文档用门禁记录里记下的同一种导出方式），与门禁记录最新一节记下的 md5 比对。不一致时先和留档 diff：属于导出噪声的，按该节处理；属于正文改动的，说明放行后 PRD 被改过，停下，按第 6 条走变更请求和变更评审。
   第 9 段（状态汇报）记录的是已经在做的工作，不因比对不一致而停下：先在该需求的 RAID 日志登记一条风险（证据引门禁记录和新旧 md5），再写进汇报的风险与阻塞。第 10 段（复盘）不做比对。
3. **放行由人拍板**：评审只出结论和证据。结论为「通过」时，先请用户逐条处置存疑项，再请用户确认放行，确认后才写入门禁记录。评审意见本身不算放行。
4. **评审对文档，不对想法**：每条问题都要引 PRD 的章节号；PRD 没写错的地方，不提替代方案。评审不等于授权改 PRD：要不要动手改、由谁改，由用户决定。
5. **轮次上限**：每个评审周期内，第 1 轮为首评，第 2、3 轮为复评（即最多两次修改 + 复评）。第 3 轮仍有阻塞项，或两路评审意见互相矛盾，结论为「升级」，交用户裁定，不自行开第 4 轮。用户裁定继续修改的，记为 `用户裁定重开评审`，PRD 修改后作为新版本重新冻结，进入下一个周期，轮次从第 1 轮重新计（周期号写进记录节标题和评审报告文件名，旧记录不覆盖）。
6. **放行后的 PRD 属于基线**：要改先提变更请求（`references/governance.md` 第 4 节）；批准后只对改动部分做变更评审（做法见 `references/prd-review-gate.md` 第 6.3 节），在门禁记录追加一节「变更评审 · CR-xxx」，记下新版本的 md5，「门禁」栏同样要有放行取值。变更评审不占评审周期的轮次，但同一个 CR 两次不通过即升级；升级后的裁定和撤回 CR 时怎么回退 PRD，见该节。受影响的任务在 CR 批准时就在台账「估算」列标 `待重估`。
7. **豁免要留痕**：用户明确要求跳过门禁时照做，在门禁记录追加一节豁免记录：当时 PRD 的 md5（云文档另记修订号，拿得到的话）、原因、日期，「门禁」栏写 `用户豁免`。之后照常按第 2 条比对 md5。同时在 RAID 日志里加一条「PRD 未评审」风险（RAID 日志还没建的，此时按模板先建出来）。豁免后 PRD 又改了的，不走变更评审（没评审过的 PRD 谈不上基线）：由用户选再豁免一次（追加一节豁免，记新 md5），或回到第 2 段正式评审。
8. **不是来自 PRD 的工作**（缺陷、运维、技术债，或用户临时给的一组任务）可以直接从第 3 段进入，不受本门禁约束；台账「PRD 出处」列必须写明具体来源，如 `无（缺陷单 BUG-123）`、`无（用户提供的清单）`。能追溯到某个 PRD 章节的任务，不得标为非 PRD 来源。

## 3 产物目录与任务台账

产物放在项目下的 `pm/`，与 PRD 同项目、不与 PRD 混放。需求级的放各自子目录，Sprint 级和项目级的放 `pm/` 根目录（一个 Sprint 通常装着几条需求）：

```
pm/
├─ 章程.md                       # 项目级，按需
├─ 决策日志/ADR-<编号>-<简称>.md  # 项目级，按需
├─ 变更请求/CR-<编号>-<简称>.md   # 项目级，按需
├─ Sprint-<n>-计划.md            # Sprint 级，n 按团队连续编号
├─ 状态汇报-<YYYY-MM-DD>.md
├─ Sprint-<n>-复盘.md
├─ 发布关卡-<版本>.md             # 每次发布
├─ 发布复盘-<版本>.md             # 发布后一周内
├─ 阶段评审-<项目>-<序号>.md      # 单个项目的阶段评审，按需
├─ 组合/                         # 组合层，按需；目录名保留，不用作需求简称
│  ├─ 组合约定.md                # 组合负责人、拍板人、成员与 pm 目录、排序规则、汇报周期、升级
│  ├─ 组合台账.md                # 成员、自报健康度与可查证的信号、排序
│  ├─ 资源分配表.md              # 每人在各成员的投入占比
│  ├─ RAID日志.md                # 只记跨成员条目；跨文件引用写 组合/R-xx
│  ├─ 依赖图.md                  # 谁在等谁、跨成员关键路径
│  ├─ 阶段评审-<成员>-<序号>.md
│  ├─ 决策日志/
│  ├─ 再分配记录.md
│  ├─ 组合汇报-<YYYY-MM-DD>.md
│  └─ 组合复盘-<YYYY>Q<n>.md
└─ <需求简称>/
   ├─ 门禁记录.md                # 第 2 段，每轮评审、变更评审、豁免各追加一节
   ├─ 评审报告-周期<c>-第<n>轮.md # 第 2 段，阻塞项 / 小问题 / 存疑明细；变更评审为 评审报告-CR-<编号>-第<n>次.md
   ├─ _门禁导出/<md5 前 8 位>.md  # 第 2 段，冻结版 PRD 留档，md5 比对不一致时 diff 用
   ├─ 任务台账.md                # 第 3～8 段共用的一张表，逐段补列
   └─ RAID日志.md                # 第 5 段建（豁免或遗留项需要登记时提前建）
```

**任务台账是唯一真源**：拆任务、估算、排优先级、建工单、排 Sprint 都往同一张表补列，不各写一份清单。
列结构和补列规则见 `references/breakdown-and-estimate.md` 第 3 节。

**编号**：任务 `T-01`；RAID 四类分别 `R-01` 风险、`A-01` 假设、`I-01` 问题、`D-01` 依赖；复盘行动项 `ACT-01`；决策 `ADR-001`；变更请求 `CR-001`。编号一经给出不复用：任务拆分写 `T-03a` / `T-03b`，作废写 `作废` 并保留行。文件里只写编号本身；跨文件引用时带上前缀：需求简称如 `公告栏/T-03`，组合层如 `组合/R-01`，跨项目如 `<项目>/<需求>/R-03`。
每个任务都要能追溯到 PRD 章节号（如 `6.2.3`）或写明非 PRD 来源；每条 RAID 条目都要引任务编号、PRD 章节号或门禁记录作证据。

## 4 从哪一段进入

用户说的事对应哪一段，就从哪一段开始；先检查那一段的输入齐不齐。

| 用户手上有 | 从这里进 | 先检查 |
|---|---|---|
| 跨团队项目刚启动 | 立章程（项目级） | 发起人、负责人、成功指标是否有人能给；给不了的标 🔵 |
| 只有诉求或 BRD | 1 写 PRD | 交 [vibe-designing]，PRD 成文后回到本 skill |
| 成文 PRD，没评审 | 2 评审 PRD | PRD 是否冻结（版本可标识） |
| 已放行 PRD | 3 拆任务 | 放行状态与 md5 比对（第 2 节第 1、2 条） |
| 任务清单，要估算 | 4 估算 | 每个任务有验收标准；没有的先补，补不了的标 `需细化` |
| 台账已估算 | 5 识别风险 / 6 排优先级 | 估算列无空值（`需拆分 / 待 spike / 需细化 / 待重估` 四种标记都算有值，但要单列） |
| 要建工单 | 7 建工单 | 用户在当前这条消息里明确说了「建」以及建到哪里 |
| 要排迭代 | 8 规划 Sprint | 有排名、有估算；本 Sprint 可用人天和历史完成区间由用户提供或从往期复盘取 |
| 要写周报 / 复盘 | 9 / 10 | 能拿到工单实际状态和团队反馈；拿不到的写 `待更新`，不推断 |
| 项目转红、要升级 | 9 状态汇报的升级写法 | 影响能否量化、有没有 2～3 个选项 |
| 要改范围、日期或已放行的 PRD | 变更请求（项目级） | 改的是不是基线；范围内的估算微调不用走 |
| 要发布上线 | 发布关卡（项目级） | 每项清单有没有具名负责人 |
| 到了里程碑，要决定继续、暂停还是停止 | 阶段评审（`references/governance.md` 第 7 节） | 章程、组合约定或上次评审有没有写下这次的门槛和停止标准，缺的不开正式评审、直接记返工；拍板人是谁 |
| 几条需求或项目同时在跑，要看整体、做组合汇报 | 组合层（`references/portfolio.md`） | 是否真需要组合层（该文件第 0 节）；组合约定有没有写，各成员的 pm 目录在哪；哪些成员还没有 RAID 日志或汇报，单列出来 |
| 人被几个项目抢、要决定谁先谁让 | 组合层的资源冲突 | 冲突是否点名到人或技能、有没有重叠窗口；排序规则写了没有；资源分配表基线是否过期 |

缺输入时，说清缺哪一项、去哪一段补，**不自己补出一个看起来合理的值**。用户只要其中一段时，只做那一段，不顺手把后面几段都跑完。

## 5 回流

- **复盘 → 下一轮规划**：复盘里的实际完成量进入历史区间；行动项 `ACT-xx` 带负责人和期限，下一份 Sprint 计划的「上轮行动项」一节逐条写进展，下一次复盘先过它们。
- **RAID → 汇报**：状态汇报的风险一节只从 `RAID日志.md` 取，写本期的状态变化（新增 / 升高 / 降低 / 关闭，假设被证伪，风险变成问题），不在汇报里新造条目；汇报中发现的新风险先登记，再写进汇报。
- **汇报 → 复盘**：汇报里的跳黄（从 🟢 直接变 🔴）、PRD 放行后改动这类过程问题，记为下一次复盘的观察。
- **门禁遗留 → RAID**：门禁记录只列遗留项；第 5 段建 RAID 日志时统一转入，凡会影响排期的登记为风险或假设，并回填编号。
- **变更请求 → PRD 与台账**：批准后做 PRD 变更评审，台账受影响任务标 `待重估`，章程、RAID、依赖约定同步更新（见第 2 节第 6 条）。
- **发布关卡 → 复盘**：每次发布后做发布复盘，产物 `发布复盘-<版本>.md`（见第 6 节「顺利也复盘」）。
- **成员 → 组合**：组合台账和组合汇报只从成员的台账、RAID 日志、门禁记录、状态汇报取数，颜色只抄成员自报，不另造；发现同根风险时，组合层登记一条，成员原条目的证据里注明 `同根：组合/R-xx`。
- **组合 → 成员**：阶段评审与再分配的决定（继续、暂停、返工、停止，加人减人）拍板后，凡改到成员里程碑、范围或已放行 PRD 的，先给该成员开变更请求，批准后再改它的 Sprint 计划、台账和资源分配表；推迟的里程碑写进该成员下一期汇报的时间线。
- **阶段评审 → 下一次评审**：每次评审写下的下次门槛和停止标准，就是下一次评审的对照基准。有条件继续的条件登记进 RAID 日志，下次复核写成条件期限，到期由汇总脚本报出、由用户安排核对；没满足的先按暂停处理。

## 6 共享约定

以下规则只在这里写一份，规程文件里只写指针。

- **不编**：进度、反馈、容量、速率、负责人、日期，拿不到就写 `待更新` 或 🔵，不推断、不给占位值。估算不默认 3 点或 M。
  例外：**有明确算式、写出了算式、并标 🔶 的推算可以用**，例如没有历史数据时的 Sprint 基线、关键路径里故事点换算天数；凭空给出的单个数值不行。
- **证据驱动**：评审问题引章节号，RAID 条目引任务、章节或门禁记录，排名写理由，复盘每条「没做好」都对应一条行动项或观察。
- **每件事一个负责人**：项目一个负责人、每个决定一个批准人、每条 RAID 一个具名负责人。共同负责等于没人负责。
- **坏消息早说**：健康度按约定口径照实给，🟡 带应对方案比假 🟢 好；⛔ 不要到截止日才第一次变红，预计兑现不了时就升级。依赖健康度为 🟡 或 🔴 的，最晚在需要日期前两个 Sprint 升级（看板团队按两个 Sprint 的天数）；`references/risk-and-priority.md` 第 1.3 节的升级触发条件先满足的，立即升级，不等这个时点。升级必带 2～3 个选项和建议。
- **顺利也复盘**：每次发布后一周内做发布复盘，线上事故也做，顺利的发布同样做。
- **速率只用来规划**：不拿来比较团队，不当作绩效向上汇报（否则估算会被注水）。
- **范围是第一个调节杆**：时间、人手、质量都卡住时，谈范围，并走变更请求；不悄悄降低质量去赶日期。
- **你做不到的事写成待办**：每周复核、按期通知、会前私下通气、按时复盘这类日历节奏或线下沟通，你在对话里没法自己执行。写进产物末尾的「需要用户做的事」或汇报的「需要的决定和支持」，不要写成已经做了。
- **发出前请用户核对**：你起草的汇报、升级、章程，发出前请用户确认里面的负责人、日期和健康度。
- **外部写操作要授权**：建工单、改工单状态、发汇报到群或云文档，都要用户在**当前这条消息**里明确同意，并说清写到哪里、写多少条；之前消息里的同意不延续到新的操作。云文档读写用用户或项目约定的工具（如 CLAUDE.md 里写明的），没有约定就问用户，不猜工具和路径。草稿阶段只产 Markdown，不碰外部系统。
- **行内标记、章节序号**沿用 [vibe-designing] 总入口，这里不复写。
- **产物的标点与标注**：写进产物（门禁记录、台账、RAID、汇报、复盘、章程等）的文字遵守 [vibe-designing] 总入口约定 14：（）说明、【】重点、code 变量值，不用直角引号。约定 13（`；` 分行、`。` 收尾）只约束 PRD 规则单元格，本链路产物不受它约束。
- **不写不做什么**：本链路沿用 [vibe-designing] 的「PRD 正文只写要做什么」。评审不因 PRD 没列「不做什么」判缺失；范围是否清楚，看功能清单和功能说明有没有写全、写清。需求级的排除项按 vibe-designing 写进 PRD 备注文档的「本期不做」一节。
- **中文输出**；术语首次出现时附英文（如 故事点 Story Points、速率 Velocity）。

## 7 交付自检

每段交付前过一遍：

- [ ] 第 3～8 段：放行状态已核对（最新一节「门禁」栏为四种放行取值之一），md5 已比对一致；或已写明非 PRD 的具体来源。第 9 段：比对不一致的已先登记 RAID，再写进风险与阻塞
- [ ] 本段的输入来自上一段的产物，没有自行补值；缺的项写了 `待更新` / 🔵；用到的推算写了算式并标 🔶
- [ ] 台账只有一份，本段补的列已填满；新任务有编号和出处
- [ ] 本段动到了基线（范围、已放行 PRD、日期、依赖约定）的，已有变更请求
- [ ] 本段规程（references 对应文件）里的自检项已逐条过
- [ ] 涉及外部系统的动作，已得到用户在当前这条消息里的明确授权
- [ ] 需要用户线下去做的事，已列成待办，没有写成已完成
- [ ] 结尾告诉用户：本段产出了什么、下一段是什么、下一段还缺什么输入
