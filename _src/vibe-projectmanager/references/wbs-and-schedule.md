# 项目级工件：WBS 与排期表

> 由 SKILL.md 第 1、3、4 节指向。本文件为本 skill 自撰：字段沿用团队现行的多维表格排期模板，推算与检查用 `scripts/schedule_calc.py`。
> 写进产物的文字按 SKILL.md 第 6 节，不用直角引号。

## 1 什么时候建、谁是真源

**什么时候建**：有发布节点、跨两个以上团队或端、或要对外承诺日期的版本，开工前起草一份排期。一个版本一份（对应多维表格里的一张数据表）。单条小需求随所在版本的排期走，不单独建。

**WBS 就是排期的父子树**：多维表格用父记录列，本地草稿用 WBS 编码列（`1` / `1.2` / `1.2.3`）。不另写一份 WBS 文件，免得两份对不上。

**谁是真源**：

| 东西 | 真源 | 说明 |
|---|---|---|
| 任务做什么、多大 | 各需求的任务台账 | 排期只在出处列引用编号，不重抄验收标准和估算依据 |
| 层级、日期、负责人、进度 | 团队的排期多维表格；建表前是本地 `排期表.md` 草稿 | 进度由各负责人在多维表格里更新，本 skill 只回读 |
| 基线 | 本地 `基线-B<n>-<YYYY-MM-DD>.csv` 快照 | 多维表格没有基线；表里加了基线列的，以快照为准，基线列只作展示 |
| 每次更新的结论 | 本地 `排期更新-<YYYY-MM-DD>.md` | 汇报和 RAID 从这里取 |

## 2 搭 WBS 骨架

**默认骨架（阶段优先）**：一级是阶段，开发阶段下按团队或端分组，叶子是具体任务。

| 一级 | 常见二级 | 对应本链路 |
|---|---|---|
| 规划阶段 | 需求、设计、评审 | 第 1 段写 PRD（交 vibe-designing） |
| 立项阶段 | 需求评审、架构方案评审、WBS排期、立项启动会 | 第 2 段 PRD 评审与门禁；章程（`governance.md` 第 1 节）；本文件 |
| 开发阶段 | 按团队或端分组（后端、前端、网关、数据……），含接口文档产出 | 第 3、4 段的台账任务 |
| 联调阶段 | 各方联调、全链路联调 | |
| 测试阶段 | 测试用例评审、各方测试、压测 | 用例与验收交 vibe-designing 套件 |
| 验收阶段 | UAT 验收 | |
| 灰度阶段 | 灰度验收 | 发布关卡（`governance.md` 第 6 节） |
| 发布阶段 | 各方发布、APP 提审 | 发布关卡 |
| 放量阶段 / 收尾阶段 | 放量观察、结项报告、发布复盘 | 发布复盘（SKILL.md 第 6 节「顺利也复盘」） |

另两种排法，一份排期只用一种：
- **团队泳道**：每个团队一组开发、联调、测试、验收、发布行，用节点列标阶段。团队多、各自节奏不同时用。
- **分批**：第一批、第二批作一级，下面再按阶段。分批上线时用。

**规则**：
1. **100% 规则**：子级合起来正好等于父级的范围，不多不少。
2. **叶子要能交付、能验**。能追溯到 PRD 的，先进该需求的台账，出处列写 `<需求简称>/T-xx`；不属于任何需求的（联调、压测、发布、提审），出处列写 `无（<具体来源>）`，与台账的非 PRD 来源同一写法。
3. **粒度**：叶子约 3 天内（与 `breakdown-and-estimate.md` 第 1 节一致），最多 4 层。
4. **一行一件事**：名称里不写日期（放日期列），不写依赖（放前置任务列）；加班、调休写进日历文件，不写成任务行；没有名称的空行删掉。
5. **门禁前只搭到阶段**：PRD 没放行时，可以先搭一级阶段、写目标日期（在备注写 `目标`），开发阶段的叶子等 PRD 放行、估算完再排（SKILL.md 第 2 节第 1 条）。

## 3 字段

沿用团队多维表格的字段名；团队模板叫法不同的，以团队的为准，脚本认的别名见 `schedule_calc.py` 开头的 COLS。

| 字段 | 用途 | 谁填 |
|---|---|---|
| 任务计划 | 名称 | 起草时 |
| 父记录（本地草稿用 WBS） | 层级 | 起草时 |
| 节点 | 所属阶段：开发、联调、测试、验收、发版、演示（灰度）…… | 起草时 |
| 团队、责任人 | 归属；责任人可多人，推算时工时按人数分摊 | 起草时；负责人由用户给，不知道写 🔵 |
| 工时（人天） | 推算工期的依据；0 表示里程碑 | 起草时（来自台账估算） |
| 前置任务（新增） | 依赖：填任务编号、WBS 或唯一的任务名；指向父级等于依赖它下面全部叶子 | 起草时 |
| 计划开始、计划结束 | 当前计划 | 推算后；之后由负责人调整 |
| 里程碑节点 | 提测、提验、发布、灰度 | 起草时 |
| 基线开始、基线结束（新增，可选） | 定基线时复制一次，之后不改 | 定基线时 |
| 出处（新增） | 台账编号或非 PRD 来源 | 起草时 |
| 进度、完成状态、状态、实际开始、实际结束、环境 | 执行情况 | 负责人 |
| 备注 | 其他 | 任何人 |

- **完成的判定**与团队的距离截止日公式一致：勾了完成状态，或进度 100%，或状态为已完成、已上线。
- **距离截止日**比的是当前的计划结束：日期一改，延期就不显示了。延期以基线比对为准（第 5 节）。
- 前置任务、基线、出处三列是本 skill 建议团队模板新增的；模板是各团队共用的，加不加由用户定。没加前置任务列的，依赖写在备注里，推算前补进本地草稿。

## 4 新建排期

**输入**：涉及的需求台账（已估算，`breakdown-and-estimate.md` 第 2 节）、工作日历（节假日、补班、请假）、各团队负责人与投入、起点日期。缺的标 🔵，不自己补。

1. **起草**本地 `pm/排期/<排期简称>/排期表.md`：骨架、叶子、工时、前置任务、责任人、里程碑节点。
2. **换算工时**：时间区间框架的估算直接作工时（人天）；故事点、T 恤尺码要用户给出比例，写出算式并标 🔶（SKILL.md 第 6 节「不编」）。
3. **推算**：`python <skill 目录>/scripts/schedule_calc.py plan 排期表.md --start <起点> --holidays <日历文件> --write 排期表-推算.md`。
   - 有工时、没填死日期的叶子，按前置任务、日历和责任人（同一人同一时间只做一件）往后排；已填计划开始和计划结束的视为定值，不动；
   - 父级日期按子级汇总；
   - 输出关键路径、浮动、同一人排队、里程碑和 Mermaid 甘特图；负浮动表示现有日期已经排不开。
4. **看结果**：关键路径上是谁、排不了的任务（没工时、循环依赖）、引用不到的前置任务、同一人的冲突。工期太长时，按 `risk-and-priority.md` 第 2.2 节的压缩办法列出选项和代价，交用户决定，不自行采用。核对无误后用 `排期表-推算.md` 替换草稿。
5. **请用户核对**负责人、日期和里程碑（SKILL.md 第 6 节「发出前请用户核对」）。
6. **建多维表格**是外部写操作：用户在当前这条消息里明确同意，并说清建在哪个多维表格、建几条，才用约定的工具写；没有约定工具的，把排期表交给用户自己导入（多维表格能导入 CSV 或 Excel）。建好后把各叶子的 record_id 对上，方便以后比对（SKILL.md 第 6 节「外部写操作要授权」）。
7. **定基线 B1**：团队认可排期后，从多维表格导出一份，`schedule_calc.py snapshot <导出> -o 基线-B1-<YYYY-MM-DD>.csv`。里程碑日期写进章程（`governance.md` 第 1 节）。进入基线后，改里程碑走变更请求（`governance.md` 第 4 节）。

## 5 更新排期

每期状态汇报前做一次。

1. **回读**：从多维表格导出当前数据（用约定的工具，或在多维表格界面导出 CSV），只读。
2. **检查**：`schedule_calc.py check <导出> --baseline 基线-B<n>-<日期>.csv --as-of <日期> --holidays <日历文件>`。导出含多张表的，加 `--table <表名>`。
3. **处理**：

| 发现 | 处理 |
|---|---|
| 计划结束比基线推迟 | 问原因；没推到里程碑之后的，记进更新记录；推到里程碑之后的，在 RAID 登记风险，证据引本次更新记录；里程碑本身要改的，走变更请求 |
| 逾期未完成 | 先核实是不是没回填。发布阶段已经过去的，多半是没回填。核实前写 `待更新`，不算延期，也不算完成（SKILL.md 第 6 节「不编」） |
| 关键路径上的任务延误超过 2 天 | 按 `risk-and-priority.md` 第 1.3 节升级 |
| 即将到期 | 写进汇报的下一期；关键路径上的提前跟负责人确认 |
| 父级日期没覆盖子级、完成情况与子级不符、数据质量问题 | 列进需要谁改哪几行，交负责人改 |

4. **写** `排期更新-<YYYY-MM-DD>.md`（模板见下）。状态汇报的时间线从这里取（`sprint-status-retro.md` 第 2.2 节）。
5. **回写多维表格**（替负责人勾完成、改父级日期）是外部写操作：默认只出清单，交负责人自己改；用户在当前这条消息里明确授权、说清改哪几行，才写。
6. **重定基线**：只在变更请求批准后，或阶段评审的结论要求时（`governance.md` 第 7 节）。新基线记为 B<n+1>，旧快照保留，更新记录里写 CR 编号。悄悄改计划日期不算重定基线。

```markdown
# 排期更新：<排期简称> · <YYYY-MM-DD>

数据来源：<多维表格名 / 数据表名>，导出于 <时间> · 基线：B<n>（<日期>）

## 结论
<一句话：里程碑守不守得住，最紧的是哪个、差几个工作日>

## 里程碑
| 里程碑 | 基线 | 当前计划 | 偏差（工作日） | 说明 |
|---|---|---|---|---|

## 本期变化
- 推迟：<行，基线日期 → 当前日期，原因或 待更新>
- 新增、删除：<行>

## 逾期与即将到期
| 行 | 负责人 | 计划结束 | 处理（核实中 / 确认延期 / 已回填） |
|---|---|---|---|

## 需要谁改哪几行
| 负责人 | 行 | 改什么 |
|---|---|---|

## 登记与升级
- RAID：<新增或更新的编号>
- 变更请求：<CR 编号或 无>

## 需要用户做的事
- <请负责人回填或核实的行，由用户转达>
```

## 6 与链路其他部分

- **任务台账**：plan 算出的关键路径和浮动，回填台账的关键路径列（`risk-and-priority.md` 第 2.2 节）。
- **Sprint**：Scrum 团队以 Sprint 计划为承诺，开发阶段叶子的日期取所在 Sprint 的窗口，排完 Sprint 再更新排期；按日期排的团队，排期表就是计划。
- **状态汇报**：时间线一节取排期更新的里程碑表，基线、当前预测、已批准变更分开写。
- **组合层**：几份排期共用人的，负责人的占用汇进资源分配表（`portfolio.md` 第 2 节），跨项目的冲突在组合层处理。
- **发布关卡**：发布阶段的里程碑日期就是发布关卡的日期。
- **配套的表**：跨团队的里程碑汇总对应章程里程碑；季度规划（路线图）属于组合层；已知缺陷台账的内容登记为 RAID 的问题，不另起一套。

## 7 自检

- [ ] 一个版本一份排期；WBS 就是父子树，没另起一份
- [ ] 叶子都能交付、能验，有出处；能追溯到 PRD 的已进台账；名称里没有日期和依赖
- [ ] 开发阶段的叶子来自已放行 PRD 的台账，或写明了非 PRD 来源
- [ ] 工时换算写了算式；故事点、T 恤尺码的比例来自用户，标了 🔶
- [ ] 负责人、日历、起点没有自己补；缺的写了 🔵
- [ ] 推算结果里的排不了、引用不到、负浮动都处理了或列给了用户
- [ ] 建表、回写多维表格都有用户在当前这条消息里的授权
- [ ] 基线有快照文件；改里程碑有变更请求；更新记录里基线和当前计划分开写
- [ ] 逾期的先核实，没核实的写了 `待更新`
