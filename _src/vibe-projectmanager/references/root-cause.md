# 项目级工件：根因分析——从问题到改进

> 由 SKILL.md 第 1、3、4、5 节指向。管的是**问题已经发生之后**：把问题记准，查到为什么会发生、为什么没拦住、为什么没早发现，再把改法落成有人负责、能核实完成的行动项，跟到处理完、复查没复发才关。还没发生、可能发生的，归 RAID 日志（`risk-and-priority.md` 第 1 节）。
> 改编自 LifeOS 的 `RootCauseAnalysis`（MIT）：按问题的样子选方法、以复盘为框架套用其他方法、各方法的成立条件与反例、原因四类与防线表、行动项强度、复查。另参考 lyndonkl/claude 的 `postmortem` 的思路，五步的划分与其工作流一致，个别短语与其相同，逐条列在 NOTICE。
> 写进产物的文字按 SKILL.md 第 6 节，不用直角引号。

## 1 什么时候做

**要做**，满足任一条：
- 线上事故，或发布后发现影响用户、业务的问题（发布复盘，见第 6 节）；
- 同一个复盘主题第二次出现在没做好里，或上一轮的行动项已经做完、问题还在；
- RAID 日志里的同一个问题第二次发生（已解决后又出现，或另一条问题的证据指向同一个环节）；
- 同一条需求或同一个依赖再次跳黄（从 🟢 直接变 🔴）：第一次跳黄记为复盘观察（SKILL.md 第 5 节），第二次说明预警又没起作用；
- 阶段评审结论为返工，且返工的原因说不清；
- 用户直接问为什么老是出这个问题。

**不做**：
- 事故还在进行：先止血、恢复，根因分析在恢复后一周内做（与 SKILL.md 第 6 节「顺利也复盘」同一时限）；这时只做一件事：把时间线和证据的位置当天记下来（列成用户待办），记忆和日志都会过期；
- 一次性的、没有可学之处的小问题：在复盘里记为观察即可；
- 代码、系统层面的排障（某个缺陷的代码原因、某次故障的技术机理）：那是工程团队的事，本规程管的是交付过程里的问题。工程团队查出的技术原因，在这里作为证据引用，接着问它为什么能进到线上、为什么没被拦住。

**同一个主题已经有分析的**，不另开一份：按第 5.3 节重开原来那份。

**问题落在哪里，文件就放在哪里**：一条需求内的放该需求目录，Sprint 层或跨需求的放 `pm/` 根目录，跨组合成员的放 `pm/组合/`，文件名 `根因分析-<简称>.md`（和事故无关的线上问题也用这个名字）；发布复盘就是 `发布复盘-<版本>.md`，按第 6 节写。

## 2 先把问题记准

分析前先写清四件事，写不清的先补证据，不急着找原因：

1. **期望和实际**：应该怎样，实际怎样。写成能核对的话，例如 `Sprint 7 承诺 12 个任务，完成 7 个`，不写 `交付不理想`。
2. **范围和影响**：哪里、什么时候、多大：影响了多少用户、持续多久、推迟了哪个里程碑、返工多少人天。实测的照写，估计的写算式并标 🔶，拿不到的写 `待更新`。
3. **时间线**：按时间列出发生了什么、当时知道什么、做了什么决定，每行注明来源（工单、汇报、RAID、门禁记录、排期更新、监控、聊天记录）。**先有时间线，再排原因**：排在前面的原因，不能建立在时间线里没有的事件上。
4. **证据在哪**：列出位置，原文不抄进来。

**当时的决定按当时能拿到的信息评价**：事后才知道的结果，不拿来说当时该想到。
**用户或团队给的猜测是假设**：照记下来，标 🔶，跟别的候选原因一样验证，不当成事实。

## 3 按问题的样子选方法

**先定框架**：线上事故、影响用户或业务的问题；跨两个以上团队；或者有几条互相独立的线索——用**无责复盘**（Blameless Postmortem，第 4.5 节）做框架，每条线索再按下面的顺序选方法。其余情况直接按下面的顺序选。

**从上往下，取第一条符合的**：

| # | 问题的样子 | 用什么 | 产出 |
|---|---|---|---|
| 1 | 这里坏那里好、这次坏上次好、时好时坏，而且有一个正常的基准可比 | **是与不是对比**（Kepner-Tregoe 问题分析的 IS / IS NOT 思路） | 对比表 + 唯一能解释所有现象的变化 |
| 2 | 本该有几道防线，却同时失守 | **故障树**（Fault Tree Analysis） | 与或门树 + 最小割集 + 共因 |
| 3 | 怀疑人、流程、工具、环境多方面都有原因 | **鱼骨图**（Fishbone / Ishikawa） | 分类原因图 + 待验证清单 |
| 4 | 一条链、一个明确的失败点 | **5 个为什么**（Five Whys） | 因果链，分叉画成树 |

是与不是对比排在最前，因为它先把范围缩小，缩小后再按 2～4 往下查。涉及人身安全、合规、资金的问题，不管用哪种方法，影响都按 `risk-and-priority.md` 第 1.2 节「影响压过概率」处理。

**中途换方法**：
- 5 个为什么问着问着分出几条平行的线索，改用鱼骨图；鱼骨图找到了是哪一类、但缺深度，在那一类里接着问 5 个为什么。
- 没有正常的基准（以前没好过、别处也没有可比的），不用是与不是对比，不编对比。
- 故障树只在有冗余防线时值得画；没有冗余、任何一处坏就出事的，用 5 个为什么。

**你拿到的只是书面证据**：工单、汇报、RAID、复盘记录、用户贴来的日志。鱼骨图要团队一起想、时间线要当事人补的部分，先给用户一份收集提纲（按第 4.2 节的分类），不替团队编原因（SKILL.md 第 6 节「不编」）；你从证据里推出来的候选原因一律标 🔶 待证实，各配一条验证待办（第 5.1 节）。

## 4 五种方法怎么写

### 4.1 5 个为什么

- 从第 2 节写准的问题开始，每问一层都写证据；没有证据的那一环写 `待查：<去哪查>`，不为凑满五层编一个原因。
- **层数不固定**：问到原因同时满足两条就停：一是流程、机制或约束层面的原因，二是改得动、有人管得着（团队管不着的组织层原因也算，改法交给管得着的人，见第 5.2 节）。⛔ 不停在 `某人疏忽`、`沟通不畅` 这类改不了的说法上，也不停在 `人手不够` 这类笼统说法上：接着问人手为什么不够、排期是怎么定的。
- 一层分出几个原因时画成树；几条分支收敛到同一个原因的，标出来，它是改一处能堵几条路的地方。
- 写完倒过来读一遍：`因为 <根因>，所以 <第 4 层>，所以 …，所以 <问题>`；读不通的地方就是缺环。

```markdown
## 5 个为什么
问题：<期望 vs 实际>
- 为什么 1：<原因> —— 证据：<>
  - 为什么 2：<原因> —— 证据：<>
    - 为什么 3a：<原因> —— 证据：<>
    - 为什么 3b：<原因> —— 证据：待查：<去哪查>
根因：<> （收敛点：<有的话>）
倒读：因为 <根因>，所以 <>，所以 <>，所以 <问题>。
```

### 4.2 鱼骨图

- **分类**：默认用下面六类，对着交付团队常见的出问题环节；团队有自己的分类就用团队的，写明用的哪一套。

| 类 | 看什么 |
|---|---|
| 人 | 技能、交接、关键人只有一个、新人上手 |
| 流程 | 评审、准入、测试、发布、变更请求哪一步缺了或被跳过 |
| 工具与环境 | 测试环境、数据、监控、工单与排期工具 |
| 需求与输入 | PRD 写漏写错、放行后改动、验收标准不清 |
| 外部依赖 | 别的团队、第三方接口、审批 |
| 组织 | 截止日期怎么定的、人怎么分的、什么被考核（第 5.2 节） |

- 每个候选原因都是假设，配一条验证方法：要什么证据、去哪查、如果真是它会看到什么。证实了的才写行动项，没证实的写验证待办。
- 某一类一条也想不出，先问是不是缺了那方面的人，不当作那一类没问题。
- 要排先后，按出现次数或影响量排，数字写来源；没有真实计数就不排比例，不编百分比。排在前面的几条接着用 5 个为什么问深。

```markdown
## 鱼骨图
问题：<期望 vs 实际> · 分类：<默认六类 / 团队自定>
| 类 | 候选原因 | 往下问一层 | 验证方法（证据 / 去哪查 / 是它会看到什么） | 状态 |
|---|---|---|---|---|
| 流程 | <> | <> | <> | 已证实 / 🔶 待证实 / 排除 |
主要原因（按 <计数来源> 排）：<>
```

### 4.3 是与不是对比

- 先写期望和实际，再按四个维度对比出问题的和本可能出问题却没出的：

```markdown
## 是与不是对比
期望：<> · 实际：<>
| 维度 | 是（出了问题的） | 不是（相近但没出问题的） | 区别 | 这期间的变化 |
|---|---|---|---|---|
| 什么 | | | | |
| 哪里 | | | | |
| 何时 | | | | |
| 多大 | | | | |
候选原因：<来自哪条变化，怎么导致的>
检验：<能解释每一条是吗 / 跟每一条不是矛盾吗>
留下的原因：<> · 怎么确认：<在测试环境去掉它问题消失、加回来问题重现；做不到的写局限>
```

- **变化窗口**从最后一次正常到第一次出问题，慢慢变坏的要往前多看。⛔ 没发版不等于没变化：数据量、定时任务、节假日与排班、人员轮换、外部依赖、配置都算变化。
- 留下的原因必须解释所有的是，并且跟所有的不是不矛盾；只是两边都有的共同条件，不能单独当作原因。
- 确认之前它仍是假设。确认只在测试环境里做，不把问题加回线上；基准或不是的那一侧观察不到的，写成局限，不编对比。
- 一直坏、全面坏、或正在抢修时不用这个方法。

### 4.4 故障树

- 顶事件写准（例如 `未经验收的版本上了线`），往下按**与门**（几件事同时发生才导致）和**或门**（任一件就导致）分解，叶子停在已知的事件、系统边界或再往下没有意义的层级。
- 列**最小割集**：同时发生就会导致顶事件的最小事件组合。只有一个事件的割集是单点，最先处理。
- **找共因**：看着是几道独立的防线，实际依赖同一个人、同一个环境、同一个外部依赖、同一次审批的，标出来；它让几道防线一起失效（与 `portfolio.md` 第 2、3 节的资源冲突、同根相通：同一个人既写又审，就是共因）。
- 以定性分析为主。有真实发生率数据时才写概率，写明数据来源与假设；各事件不独立时，不套独立事件的概率公式。
- 割集里要几件事同时发生，不能单独当作安全的证据：先查有没有共因，再看单个事件本身是不是常发生。

```markdown
## 故障树
顶事件：<>
- 或：<顶事件>
  - 与：<中间事件 A>
    - <基本事件 1>
    - <基本事件 2>
  - <基本事件 3>
最小割集：{1, 2}、{3}（单点）
共因：<1 和 2 都依赖 <>，不独立>
先处理：<单点与共因>
```

### 4.5 无责复盘（框架）

五步，前四步出记录，第五步跟到关闭：

1. **立案**：按第 2 节记准问题、影响和时间线。
2. **查因**：原因分四类写，每类按第 3 节选方法：
   - **直接原因**：什么直接触发了问题；
   - **系统因素**：什么让直接原因有机会发生（有证据的有几条写几条，不为凑数编）；其中属于组织层的（第 5.2 节）单独标出；
   - **发现慢在哪**：为什么没早知道；
   - **恢复慢在哪**：为什么花了这么久才恢复。
   再画一张**防线表**：本该拦住它的每一道防线（评审、准入、测试、发布关卡、灰度、监控），这次各自的漏洞在哪。
3. **定改法**：按第 5 节。
4. **核对后交用户分享**：记录给用户核对后，由用户决定发给谁；发到群或云文档按 SKILL.md 第 6 节「外部写操作要授权」。
5. **跟到关闭**：按第 5.3 节。记录写完不等于复盘结束。

做得好的照写：顺利的环节也要知道是为什么顺利，下次照做。最后写**经验**：这次以后知道了、以前不知道的事。

## 5 把方案落成改进

### 5.1 行动项与验证待办

**已证实的原因**，每个至少对应一条行动项，每条写：具体动作、强度、负责人、期限、怎么核实完成、去向、状态。
**🔶 待证实的原因**，各对应一条验证待办：谁、哪天前、查什么，列进「需要用户做的事」；证实后补行动项，排除的划掉并写依据。

**编号**：文件内行动项编 `ACT-01` 起；别的文件引用时带文件前缀，如 `根因分析-发布延期/ACT-01`（SKILL.md 第 3 节）。

**强度**（从强到弱）：

| 强度 | 例子 |
|---|---|
| 消除：问题不再可能发生 | 下线有风险的手工步骤、删掉没人用的旁路 |
| 强制或自动化：不做就过不去 | 准入检查不过就进不了 Sprint、发布流水线强制跑回归 |
| 简化或标准化 | 统一模板、减少交接、写清检查清单 |
| 培训 | 讲一次、带一次 |
| 提醒或文档 | 在群里提醒、补一段说明 |

- 主要几条只有培训、提醒、要人更上心的，说明诊断还停在人身上，回到第 4 节再往下问一层。
- 动作要能照着做、做完能查，不写方向性的口号；负责人写具体的人，不写 `团队`，不知道写 🔵；核实写成可检查的结果，例如 `下 3 次发布的发布关卡记录里都有回归结果`。
- **去向**：
  - 要开发或配置的工作 → 工作落在哪条需求，就进那条需求的台账，新任务 `T-xx`，出处写 `无（根因分析-<简称>/ACT-xx）`（SKILL.md 第 2 节第 8 条），按准入进 Sprint；落不到某条需求上的流程改进，只作为行动项跟踪，不进台账；
  - 还可能再发生的 → RAID 风险，证据引本文件，缓解措施写 `减轻：T-xx`；
  - 改到里程碑、范围、已放行 PRD 的 → 变更请求；
  - 团队定不了的 → 交拍板人的决定（第 5.2 节）。
- **状态**：未开始 / 进行中 / 完成待核实 / 已核实 / 放弃 / 不采纳。
  - **放弃**：写理由和同意的人，改在本文件里；Sprint 复盘里不能直接放弃根因分析的行动项（`sprint-status-retro.md` 第 3 节）。
  - **不采纳**：拍板人决定不改的，在 RAID 日志里登记一条风险，策略写接受，带应急预案和启用的触发条件（`risk-and-priority.md` 第 1.4 节），这条行动项就算处理完。
- 行动项条数不设上限，但每条都要对应一个已证实的原因。Sprint 复盘的行动项 ≤ 3 条只管复盘本身，复盘里转出的根因分析，在复盘里只占一行 `对应：根因分析-<简称>`。

### 5.2 组织层原因：改的是约束，不是人

症状是**总是赶工、没时间测试、测试被压到最后、需求一直插队、一直在救火、同一个人到处被叫**时，往下问通常会落到组织层：

| 组织层原因 | 怎么查证 | 改法落在本链路哪里 | 谁拍板 |
|---|---|---|---|
| 截止日期不现实：日期先定、估算后补，或承诺高于历史完成区间 | 承诺 vs 历史区间（`sprint-status-retro.md` 第 1.2 节）；章程、排期里日期定在估算之前；排期基线一再后推 | 承诺取历史区间低端；日期按估算区间定；改日期走变更请求；范围是第一个调节杆 | 拍板人 |
| 资源约束：人被几头同时占用、关键技能只有一个人 | 资源分配表与资源冲突（`portfolio.md` 第 2 节）；同一个人出现在几条问题的时间线里 | 资源冲突的五种解法；故障树里标出的共因 | 拍板人 |
| 激励错位：只考核按期上线或交付数量，质量问题不进任何人的指标，救火有人表扬、预防没人看 | 章程成功指标只有日期没有质量护栏；发布关卡被跳过；速率被拿去比较团队 | 章程成功指标加护栏指标；发布关卡要真能叫停；速率只用来规划 | 拍板人 |
| 范围不受控：放行后频繁改、口头加需求 | 变更请求与 PRD 变更次数、门禁记录、计划外工作占比 | 变更请求；PRD 门禁 | 拍板人 |

表中的拍板人按 `risk-and-priority.md` 第 1.2 节「影响压过概率」那一句的顺序取：发起人；没有发起人时为用户；有组合层时为组合拍板人。

- 查到这一层，⛔ 不写多加班、提高意识、注意时间这类行动项：根子在约束上，改人的行为治不了。团队自己能做的改进可以并列写，但不能代替组织层的改法。
- 组织层的改法写成交给拍板人的决定，按 `sprint-status-retro.md` 第 2.5 节的升级写法：影响按进度、成本、质量量化，带证据、2～3 个选项与建议，写明谁在哪天前定。这个决定同时抄进下一期状态汇报（有组合层的抄进组合汇报）的「需要的决定和支持」，这样才到得了拍板人手上；正式提出前先跟拍板人单独通个气，列成用户待办。你只起草，不替拍板人定。
- 组织层的结论要有两次以上的发生或数据撑着；只有一次、或只是感觉的，标 🔶，先记为观察，下次再出现时合并。
- 同一个已证实的组织层原因压在两个以上组合成员上的，按 `portfolio.md` 第 3 节登记一条同根。

### 5.3 跟到关闭

- **行动项的进展跟着谁走**：有 Sprint 的，列进下一份 Sprint 计划的「上个 Sprint 行动项进展」，下一次复盘先过它们（`sprint-status-retro.md` 第 3 节）；看板团队、项目层的分析，写进下一期状态汇报的进展一节；组合层的，写进下一期组合汇报。落到台账、RAID 的，再跟着各自的节奏复核。
- **复查窗口**要覆盖足够多次同类机会，否则没复发说明不了什么：按问题出现的节奏，至少覆盖 3 个 Sprint 或 2 次发布，且不少于 30 天。复查日写成算式 `最晚的行动项期限 + 窗口` 并标 🔶，例如 `ACT-02 期限 12-05 + 3 个 Sprint（6 周）= 01-16`；用户给了日期的照用。行动项期限还是 🔵 或 `待更新` 的，复查日也写 `待更新`，期限定下后再算。
- 复查看两件事：行动项是不是都已核实、放弃或不采纳；同类问题有没有再出现。复查由用户安排，列成待办。
- **分析针对的是 RAID 里的问题时**：已解决后复发的，把原条目改回处理中，证据补上 `根因分析-<简称>`；另一条问题指向同一环节的，两条都挂上。行动项全部处理完之前，按 `risk-and-priority.md` 第 1 节的表每周复核；全部处理完后，下次复核改为复查日；复查通过才改为已解决。
- **复查时又出现了**：先核对是不是同一个机理：机理不同的是另一个问题，另开分析。机理相同的，重开这份分析，状态回到跟踪中，往下再问一层或换方法，行动项强度往上提一档。**同一份分析第二次重开**时，不再往下挖：按第 5.2 节写成交拍板人的决定（接受现状、加资源，还是改范围或日期）。
- **文件状态**：
  - **草稿**：在写；
  - **待验证**：主要原因都还是 🔶，验证待办已列出、带日期；到期后回来改；
  - **跟踪中**：至少一个原因已证实、有行动项，复查日已定（或写了 `待更新`）；
  - **已关闭**：行动项全部已核实、放弃或不采纳，并且复查通过；全部行动项被放弃或不采纳的，在结论里写明接受现状。
  只有满足已关闭的条件才写已关闭。

## 6 发布复盘

每次发布后一周内做（SKILL.md 第 6 节「顺利也复盘」），产物 `发布复盘-<版本>.md`：
- **有事故或明显问题的**：按第 4.5 节无责复盘写全，用第 8 节的根因分析模板；
- **顺利的**：用第 8 节的发布复盘简版，只写概要、做得好、没做好、行动项、指标和经验。简版的行动项对应没做好的条目，和 Sprint 复盘一样不超过 3 条，不要求已证实的原因；没做好的有复发迹象的，另开根因分析。

## 7 底线

- **对流程，不对人**（SKILL.md 第 6 节「对流程，不对人」）：写哪个环节放过了它，例如 `发布流程没有要求验收结论`；不写谁漏了什么。记录里不出现个人评价，不和绩效谈话放在一起。
- **不围着一个早就看中的原因组织材料**：先时间线，后原因；每个原因都过一遍证据。
- **不编**：原因、比例、概率、对比都要有来源；证据撑不起的写成假设或缺口，不为凑数补因素。
- **结论交出去时已经做完**：交给用户的分析里，没有还在查的环节被写成结论；没查完的明确写 `待查`。
- **你做不到的事写成待办**：访谈当事人、组织复盘会、跟拍板人谈、按期复查、验证待办，列进「需要用户做的事」。

## 9 自检

- [ ] 问题写成了期望 vs 实际，范围与影响写了来源或算式；时间线先于原因写好，每行有来源
- [ ] 方法按第 3 节的顺序选，写明了用的哪种；事故、跨团队、几条线索的用无责复盘做框架；换方法的写了原因；不是工程排障
- [ ] 每个原因都有证据，没有证据的标 🔶 或 `待查`；用户和团队的猜测当作假设验证过；没有编比例和概率
- [ ] 5 个为什么停在改得动、有人管得着的流程或约束上，没停在某人疏忽；倒读通顺
- [ ] 是与不是对比留下的原因解释了所有的是、不跟任何一条不是矛盾，只在测试环境确认；故障树标了单点和共因
- [ ] 每个已证实的原因都有行动项，写了强度、具体的负责人、期限、怎么核实、去向、状态；每个 🔶 原因都有带日期的验证待办；主要几条不只是培训和提醒
- [ ] 症状指向组织层的，写成了交拍板人的决定：影响量化、带证据和选项，已抄进下一期汇报，通气列成待办；没有用改人的行为代替
- [ ] 全文对流程、不对人，没有个人评价
- [ ] 复查日按算式写了（或写 `待更新`），窗口覆盖足够次数；行动项进了 Sprint 计划或汇报、台账、RAID；被分析的 RAID 问题状态与复核日期按第 5.3 节改了
- [ ] 文件状态与第 5.3 节的条件相符；重开的核对了机理，第二次重开已转交拍板人
- [ ] 顺利的发布复盘用了简版
- [ ] 访谈、开会、分享、通气、复查、验证列成了用户待办
