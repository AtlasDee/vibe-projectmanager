# 第 3、4 段：拆任务与估算

> 由 SKILL.md 第 1、3 节指向。改编自 agnostic-planning-skills 的 `plan-tickets`（拆分原则、只出草稿）与 `estimate-tasks`（估算框架、置信度、拆分与 spike）；
> 三点估算、估算分歧处理、验收标准质量要求、拆分粒度取自 skills-ws `project-management`。

## 1 拆任务

**入口**：按 SKILL.md 第 2 节第 1、2 条核对放行状态并比对 md5；非 PRD 来源的工作按第 8 条写明具体来源。

1. 通读已放行的 PRD：需求功能清单 → 每个功能模块的功能说明表、字段表、状态-操作矩阵、权限与日志表。
2. **按能独立完成、独立验证来拆**：一个任务做完后，能单独验收。目标粒度是**一个人约 3 天内能做完**；拆不开的不硬拆，在备注里写原因。
3. 每个任务写：标题、出处（PRD 章节号或非 PRD 的具体来源）、要做什么（一两句）、验收标准、依赖（任务编号）、备注（技术约束、待确认点）。
4. 验收标准从 PRD 规则直接转写，写成能判通过 / 不通过的句子；PRD 里有 🔵 的，任务里照样标 🔵，不替 PRD 定口径。
   质量要求：覆盖正常路径**和**明显的异常、报错路径；测试人员不看代码就能判断通过与否。不合格：登录正常。合格：已注册用户输入正确密码，进入首页并生成会话；连续 5 次密码错误，账号锁定 15 分钟。行为类的验收也可以写成「假如 / 当 / 那么」（Given / When / Then）三段。
5. 按依赖顺序排列：先基础（数据、接口），后上层（页面、交互），最后收尾（日志、埋点、联调）。
6. ⛔ **不编团队政策**：负责人、Sprint、标签、工单前缀、状态流转，项目没规定就不写。
7. 只产台账草稿，不碰工单系统（建工单是第 7 段）。

**常见拆法**（按团队需求的典型形态，供参考，不强制）：

| PRD 内容 | 通常拆成 |
|---|---|
| 一个后台功能模块（列表 + 筛选 + 新增编辑 + 状态操作） | 接口与数据 / 列表与筛选 / 新增编辑表单 / 状态操作与二次确认 |
| 权限节点表 | 权限点配置（可并入对应模块任务，写明验收） |
| 操作日志表 | 日志记录（集中一个任务，按模块列出要记的操作） |
| 前台 ToC 展示 | 数据过滤链 / 展示与空态 / 动效 / 埋点 |

## 2 估算

**入口**：台账里每个任务都有验收标准；没有的标 `需细化`，不估。

1. **定框架**：问用户或沿用项目已有的；一张表只用一种，中途换框架就整表重估。

| 框架 | 刻度 | 适用 |
|---|---|---|
| 故事点 Story Points（斐波那契） | 1 极小 · 2 小 · 3 中 · 5 大 · 8 很大（建议拆）· 13（必须拆） | 有历史数据的 Scrum 团队，比相对复杂度 |
| T 恤尺码 | XS · S · M · L（建议拆）· XL（必须拆） | 粗估、路线图、给业务方看 |
| 时间区间 | <1 天 · 1～2 天 · 3～5 天（建议拆）· 1～2 周（必须拆）· 2 周以上（必须拆） | 要对日历承诺的项目 |
| 三点估算 | （乐观 + 4 × 最可能 + 悲观）÷ 6，三个值都写出来 | 风险高、不确定的个别任务；可与上面任一框架配合，结果换回该框架的刻度 |

   「建议拆」对应第 1 节约 3 天的粒度：能拆就回去拆，拆不开的在备注里写原因后保留。

2. **逐个估**：看范围、未知点、是否还要再拆。估的是相对复杂度，不是谁来做要几天（时间区间框架除外）。
3. **每个估算都带置信度**：高 / 中 / 低，并在备注里写依据（同类模块做过、接口文档未出）。
4. **标记**（写在「估算」列，代替数值）：
   - `需拆分`：落在必须拆的档位，回第 1 节拆完再估；
   - `待 spike`：置信度低、因为有技术未知，建议一个限时预研任务（写明时长和要回答的问题），预研完再估；
   - `需细化`：没有验收标准；
   - `待重估`：PRD 变更评审影响到的任务（SKILL.md 第 2 节第 6 条），原估算移到备注，重估后替换。
   依赖 🔵 口径的任务，置信度不高于「中」，备注写依赖哪条 🔵。
5. ⛔ 不给占位值：看不懂的任务不估，问清楚；不默认 3 点或 M。
6. **团队估算有分歧时**（例如估算会上各人差了两档以上），不取平均，先讨论差异来自哪里（对范围理解不同、有人知道某个坑），讨论完再估。
7. 估算是预测，不是承诺：对外给的是区间和置信度，不拿单个数字去追责。

## 3 任务台账（唯一真源）

`pm/<需求简称>/任务台账.md`，第 3 段建表，后面各段只补列、不另起表。写进文件的文字按 SKILL.md 第 6 节，不用直角引号。

```markdown
# 任务台账：<需求名>

- PRD：<路径或云文档名> · 已放行版本：md5 <值>（门禁记录 <周期 c 第 n 轮 / 变更评审 CR-xxx / 豁免>；变更评审放行后更新这一行）
- 估算框架：<故事点 / T 恤尺码 / 时间区间>
- 排序框架：<RICE / MoSCoW / 价值-投入 / WSJF>

| ID | 任务 | 出处 | 依赖 | 估算 | 置信度 | 得分 | 排名 | 关键路径 | 工单号 | Sprint | 状态 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| T-01 | 公告列表接口 | 6.1.3 | — | 3 | 高 | | | | | | |
| T-02 | 列表页与筛选 | 6.1.3 | T-01 | 5 | 中 | | | | | | |

## 任务详情

### T-01 公告列表接口
- 要做什么：……
- 验收标准：
  - [ ] ……
- 备注：……
```

| 列 | 哪一段填 | 说明 |
|---|---|---|
| ID / 任务 / 出处 / 依赖 | 3 拆任务 | 出处写 PRD 章节号，或 `无（<具体来源>）` |
| 估算 / 置信度 | 4 估算 | 可写 `需拆分`、`待 spike`、`需细化`、`待重估` |
| 得分 / 排名 | 6 排优先级 | 排名为全序，不并列 |
| 关键路径 | 6 排优先级（做关键路径分析时；有排期表的取排期推算结果） | 在路径上写 `●`，其余写浮动天数；不做时留空 |
| 工单号 | 7 建工单 | 只填真实建成的；草稿阶段留空 |
| Sprint | 8 规划 Sprint | 选中的写 Sprint 编号；没选中的留空 |
| 状态 | 9 状态汇报时按工单实际状态更新 | 取工单系统的状态名；任务作废写 `作废` |

## 4 交付格式

- **拆任务**：台账（ID 到依赖四列）+ 任务详情；末尾写任务总数、按 PRD 章节的分布、有 🔵 的任务数。
- **估算**：说明用了哪个框架、为什么；补完估算两列；单列 `需拆分 / 待 spike / 需细化 / 待重估` 清单，每条写原因；汇总总量（不含这四类，另写各有几个）、置信度分布。

## 5 自检

- [ ] 每个任务都有出处（PRD 章节号或具体的非 PRD 来源）、验收标准，能独立验收；验收覆盖了异常路径
- [ ] 粒度约 3 天；拆不开的写了原因
- [ ] 按依赖排序，依赖只指向已有编号
- [ ] 没写项目没规定的负责人、Sprint、标签、状态
- [ ] 一张表只用一种估算框架；每个估算都有置信度和依据，没有占位值
- [ ] 必须拆的已标 `需拆分`，技术未知已标 `待 spike` 并给出预研建议
