# 项目级工件：章程、干系人、决策、变更、发布关卡、阶段评审

> 由 SKILL.md 第 1、2 节指向。这些不是链路里的某一段，而是贯穿全程、按需建立的工件，都放 `pm/` 根目录。
> 改编自：skills-ws `project-management`（章程与启动清单、RACI、DACI 与 ADR、变更请求、完成标准、发布就绪清单、OKR）；
> project-execution（干系人地图与沟通节奏、发布 Go / No-Go 关卡），及其 references 的 `stakeholder-communication`（干系人清单、按阶段的沟通节奏、难谈的话）；
> 阶段评审改编自 hard-half 的 `portfolio-stage-gate`（资源决定而非状态会、门槛事先写好、空头继续改判暂停、不计沉没成本、证据随投入加码）与 management-consulting-plugin 的 `project-governance`（有条件继续的条件落到人和日期、过了评审不等于风险消失）。
> 写进这些工件的文字按 SKILL.md 第 6 节，不用直角引号。

**什么时候要建**：单个小需求只走链路即可。跨团队协作、有对外发布节点、有预算或明确发起人的项目，开工前先立章程；其余工件在需要时建，不为建而建。

**没有章程或发起人时**：本文件里写着由发起人批准、拍板的地方（变更请求、发布结论），一律由用户批准。

## 1 项目章程与启动清单

一页纸，开工前让所有人对齐。写好后请发起人确认，在工单系统或项目文档里挂链接。

```markdown
# <项目名> 章程

发起人：<对结果和预算负责的一个人>
负责人（DRI）：<唯一对交付负责的一个人>
日期：<YYYY-MM-DD>　状态：草稿 / 已确认

## 问题与为什么是现在
<一到三句：什么问题、谁遇到、不解决的代价>

## 目标与成功指标
- <可度量的结果，例：结算转化率提升 3 个百分点（Q4 前）>
- <护栏指标，不能变差的，例：p95 响应保持在 400ms 以内>

## 范围
<要做的事，逐条；对应的 PRD 链接>

## 里程碑（规划前是目标，规划后才是承诺）
- M1 <名称> —— <日期>（有排期的，取排期基线的里程碑日期，见 wbs-and-schedule.md 第 4 节）
- M2 <名称> —— <日期>

## 团队与预算
<人数、费用、基础设施>

## 关键风险与假设
<前 3 条，链 RAID 日志编号>

## 决策权
<DACI，见第 3 节>

## 健康度口径
<🟢 / 🟡 / 🔴 的判定标准，默认定义见 sprint-status-retro.md 第 2.1 节>
<有组合层时，排序规则、升级层级与时限写进组合约定（portfolio.md 第 0 节），不写在这里>

## 首个阶段评审
<日期 · 门槛（达到什么算可以继续）· 停止标准（看到什么就停）· 评审人 · 拍板人；见第 7 节>
```

- 成功指标写**结果**（转化率、时长、留存），不写上线某功能；做完就能打勾的是举措，不是指标。组织用 OKR 时，把这里的指标对到某条关键结果 KR 上，评分只评 KR、不评举措，不跟奖金挂钩（否则目标会被压低）。
- **范围只写要做的事**（SKILL.md 第 6 节「不写不做什么」）。需求级的排除项写进对应 PRD 的备注文档；跨需求、难以撤回的范围取舍才另记一份 ADR（第 3 节）。之后有人要加进来，走变更请求（第 4 节）。
- 发起人和负责人**各只有一个**（SKILL.md 第 6 节「每件事一个负责人」）。

**启动清单**：

- [ ] 章程已写，发起人已确认
- [ ] 唯一负责人已指定
- [ ] 问题、成功指标、护栏指标已定义
- [ ] 干系人已识别，RACI 已填（第 2 节）
- [ ] 里程碑已列
- [ ] 依赖已梳理，具名负责人和日期已写（RAID 依赖表）
- [ ] RAID 日志已建
- [ ] 沟通计划已约定，RAG 口径已约定
- [ ] 技术方案已评审，关键决定已记入决策日志

## 2 干系人与沟通

**干系人地图**：按影响力 × 关注度分四格。

| | 关注度高 | 关注度低 |
|---|---|---|
| **影响力高** | 重点管理：直接、频繁地同步 | 保持满意：定期给摘要 |
| **影响力低** | 随时告知：任务层面的沟通 | 广播即可 |

把人放错格子是项目摩擦的常见来源，拿不准的问用户。四格的打法：重点管理的人直接、频繁、详细地同步，重要决定请他参与；保持满意的人给摘要，坏消息主动先说，别让他意外；随时告知的人定期广播，涉及他那块的请他提意见；其余的只在大范围通知里带上。

**干系人清单**（重点管理、保持满意两格里的人逐个写；人名和偏好来自用户，不编）：

| 姓名 | 角色 | 所在格子 | 最关心什么（进度 / 质量 / 成本 / 范围） | 偏好渠道 | 频率 | 能拍板什么 | 已知偏好 |
|---|---|---|---|---|---|---|---|

已知偏好指的是像要数据不要故事、要选项不要问题这类，写给汇报和升级时参考。

**RACI**：每一项工作谁负责执行（R）、谁拍板（A，每行只有一个）、征求谁的意见（C）、通知谁（I）。下表是示例，按团队实际分工填：

| 事项 | 产品 | 研发负责人 | 设计 | 发起人 |
|---|---|---|---|---|
| 需求（PRD） | R / A | C | C | I |
| 技术方案 | C | R / A | I | I |
| 交互设计 | C | C | R / A | I |
| 上线决定 | R | C | C | A |

**沟通计划**：

| 受众 | 角色 | 频率 | 渠道 | 内容深度 |
|---|---|---|---|---|
| 发起人 | 出资方 | 按下方节奏表（默认每周）+ 随时 | 邮件 / 一对一 | 执行摘要 |
| 依赖方团队 | 依赖 | 每周 | 群 / 邮件 | 只有依赖状态 |
| 项目组 | 执行 | 每天 | 站会或异步日报 | 完整 |

人名、渠道由用户给出，不编。远程或跨时区团队默认写成文、异步同步，同步会议只用来做决定和解阻塞。

**节奏随阶段调整**（默认值，按团队实际改；收尾冲刺指离发布或最后一个里程碑不到两个 Sprint，看板团队按相应天数）：

| 阶段 | 发起人 | 项目组 | 其他干系人 |
|---|---|---|---|
| 规划、执行前中期 | 每周 | 每天站会 | 立项时发启动通知，之后每两周一份摘要 |
| 收尾冲刺 | 每周两次 | 站会 + 每天一次对齐 | 每周一份摘要 |
| 发布周 | 每天 | 随时 | 发布通知 |
| 上线后 | 每周，持续两周 | 每天，持续一周 | 上线总结 |

### 难谈的话

这些话由用户去说，你负责起草要点，并把要做的事列进待办。

- **向发起人报坏消息**：会前先私下打招呼，用一句话说明问题，并说明已有几个方案可谈，别让他在会上第一次听到。开口先说影响（例：4 月 15 日的截止日大约要晚两周）。不归咎他人，「我该早点提出来」比「某团队掉链子了」更能赢得信任。坏消息和出路一起给，最后要一个具体决定，例如请他在周五前定是否砍范围，而不是问「怎么办」。
- **谈范围变更**：说成取舍而不是失败，例如为保住 4 月的日期，建议把某功能挪到二期。量化放弃什么、保住什么，同时给出保留全部范围时的新日期。对方口头点头不算数，同意后走变更请求（第 4 节）留书面记录。
- **干系人意见不合**：先找分歧根源。信息不同的，先摆数据、对齐事实；优先级不同的，交给能仲裁的人，通常是发起人；风险承受度不同的，把风险写明白，交拍板人定。定下来的记进决策日志（第 3 节），已定的事不反复重议。

## 3 决策日志（DACI + ADR）

记的是**为什么**，不只是做了什么。后来的人最需要的是当时的理由。

- **DACI** 定决策权：推动者 Driver（推动出结论）、批准人 Approver（一个人签字）、参与者 Contributors（征求意见）、知会 Informed。写进章程，免得决定卡住。
- **ADR** 记结果：每个重要决定一份短文档，编号，**定稿后不改**；要推翻就写一份新的，旧的标「已被 ADR-xxx 取代」。

**什么时候记**：难以撤回的、影响多个团队的、半年后会有人问当初为什么这么做的。能随时撤回的小决定不用记，快速决定、继续往下。

`决策日志/ADR-<三位编号>-<简称>.md`：

```markdown
# ADR-007：<决定标题>

日期：<YYYY-MM-DD>　状态：提议 / 已接受 / 已被 ADR-xxx 取代
推动者：<>　批准人：<>　参与者：<>

## 背景
为什么现在要定：约束、需求、要解决的问题。

## 备选方案
1. <方案> —— 优点 / 缺点
2. <方案> —— 优点 / 缺点　← 选定

## 决定
我们选 <X>，因为 <接受了什么取舍>。

## 影响
好处：<>　代价：<>　后续：<由此产生的 ADR 或工单>
```

## 4 变更请求

范围蔓延是悄悄发生的。章程范围、已放行的 PRD、里程碑日期（含排期基线快照，`wbs-and-schedule.md` 第 4 节）、预算、冻结的依赖约定合起来是**基线**；动到基线的，一律走变更请求，不直接改。

- 范围内的估算微调是正常的 Sprint 维护，**不用**走变更请求。
- 涉及 PRD 的变更：变更请求批准时，受影响任务在台账估算列标 `待重估`；PRD 改动部分做变更评审（SKILL.md 第 2 节第 6 条）。CR 后来撤回的，PRD 要回退，做法见 `prd-review-gate.md` 第 6.3 节。
- 每个被批准的变更请求，同步更新章程、计划，以及相关的依赖约定和 RAID 日志。

`变更请求/CR-<三位编号>-<简称>.md`：

```markdown
# CR-014：<变更标题>

提出人：<>　日期：<YYYY-MM-DD>　状态：提议 / 批准 / 拒绝
变更内容：<改什么，原来是什么>
价值：<为什么要改>
影响：进度 <+n 个 Sprint> · 范围 <挤掉哪些任务> · 风险 <新增的 RAID 条目>
选项：(a) 现在加，<里程碑> 推迟 <n>　(b) 先发布，下一版再做　(c) 不做
决定（批准人：发起人；没有发起人时为用户）：____　日期：____
```

## 5 完成标准 Definition of Done

团队统一，不按单个任务定。默认：代码已评审、持续集成测试通过、验收标准满足、文档或变更说明已更新、有风险的功能挂了开关、已部署到测试环境、日志 / 指标 / 告警已就位。完成指可以发布，不是在我电脑上能跑。团队有自己的标准时以团队的为准，写进章程。

## 6 发布关卡 Go / No-Go

不在上线会上临时决定发不发。关卡提前定好，每一项有具名负责人签字。关卡要真能叫停：清单项是能判通过 / 不通过的标准，负责人有权判 No-Go；一个从来没拦下过任何东西的关卡，只是走过场。有对外发布的项目每次发布过一次；单条小需求随所在版本的发布关卡一起过，不单独做。

**发布就绪清单**：

- [ ] 承诺的范围都已完成（满足完成标准），或已通过变更请求移出
- [ ] 验收标准已验证；没有未关闭的严重 / 高等级缺陷（业务验收可用 [vibe-designing-acceptance] 出线上验收记录）
- [ ] 发布方案：灰度比例、成功指标、**回滚步骤已演练过**（不只是写了）
- [ ] 功能开关已接好，紧急关闭已在测试环境验证
- [ ] 监控大盘、告警、上线时段的值班负责人已就位
- [ ] 性能已按护栏指标验证
- [ ] 安全与隐私已评审（权限、个人信息、密钥）；受监管业务的合规签字已拿到
- [ ] 数据迁移可回退或已备份，并在类生产数据上演练过
- [ ] 文档、客服手册、对外通知已准备好

里程碑上要不要继续投入，不在发布关卡里判，走第 7 节的阶段评审。

**结论**（由各关卡负责人逐项表态，发起人拍板；没有发起人时由用户拍板）：

| 结论 | 条件 |
|---|---|
| ✅ Go | 清单全部满足 |
| ⚠️ 有条件 Go | 少数项未满足，但都有具名负责人、期限和兜底措施，拍板人接受 |
| ⛔ No-Go | 有影响主流程或无法回退的项未满足；写明补救计划和下次评审时间 |

结论记入 `发布关卡-<版本>.md`（逐项结果 + 签字人 + 结论）。通知所有干系人（建议 24 小时内）、上线后盯成功指标和护栏指标，由用户安排，列进「需要用户做的事」。发布后做发布复盘（SKILL.md 第 6 节「顺利也复盘」，写法见 `root-cause.md` 第 6 节）。

> 发布关卡设「有条件 Go」，PRD 门禁不设：PRD 门禁防的是在会变的文档上估算排期；发布时剩余事项可以带着兜底措施上线，由拍板人承担。

## 7 阶段评审：要不要继续投入

阶段评审回答一个问题：这个项目（或组合里的一个成员）**下一阶段还要不要继续投人投钱**。它是资源决定，不是状态会：只念进度、不做决定的会，不叫阶段评审。

**三种关卡各管各的**：

| 关卡 | 判什么 | 结论 |
|---|---|---|
| PRD 门禁（SKILL.md 第 2 节） | 这份 PRD 能不能拿来拆任务、估算 | 放行 / 未放行 |
| 发布关卡（第 6 节） | 做好的东西能不能上线 | Go / 有条件 Go / No-Go |
| 阶段评审（本节） | 下一阶段要不要继续投入 | 继续 / 有条件继续 / 暂停 / 返工 / 停止 |

**什么时候评**：在章程或组合约定（`portfolio.md` 第 0 节）里事先定好的里程碑上评，一次只评一个项目或成员。小的试验不必过很多关，评审的次数和项目的投入相称。

**评审人与拍板人**：评审人是下一阶段要拿出人和钱的那几位，由他们给意见，因为继续与否花的是他们的资源。**拍板人只有一个**：单个项目为发起人（没有发起人时为用户），组合里的成员为组合拍板人（`portfolio.md` 第 0 节）。结论需要变更请求的，拍板人在评审时一并批准，变更请求的批准人写这位拍板人，并引用评审文件。

**门槛要事先写好**：第一次评审的门槛和停止标准，立项时写进章程的「首个阶段评审」一节（第 1 节模板），或写进组合约定；之后每次评审结束前，写下下一次的门槛（达到什么算可以继续）和停止标准（看到什么就停）。评审时对照事先写好的门槛判断，**不临场改门槛**；需要改的，记一份 ADR 说明为什么改。投入越大的阶段，门槛要求的证据越硬。**缺门槛或缺停止标准的，不开正式评审，结论直接记为返工**：先补上，再约评审。

**结论五选一**：

| 结论 | 什么时候用 | 必须写清 |
|---|---|---|
| 继续 | 证据达到了上次写的门槛 | 下一阶段的人（具名或占比）、钱（涉及的话）、下次评审日期、下次的门槛与停止标准。缺任何一项，这就是空头继续，改判暂停 |
| 有条件继续 | 门槛大部分达到，没达到的几项有补救办法 | 继续一行的全部必填项，外加条件表：每个条件落到具名负责人和期限，并在 RAID 日志登记为一条问题，下次复核写成条件期限，证据引本评审文件，到期由汇总脚本报出。条件到期没满足的，先按暂停处理，直到重新评审；重评时对照条件本身和原定门槛 |
| 暂停 | 在等一个证据、一个人或一笔钱 | 等的是什么、最晚等到哪天、到期没等到怎么办；暂停期间不追加投入。等对齐、等确认之后再继续，都算暂停 |
| 返工 | 缺门槛或停止标准，或证据不足以判断 | 回到哪一步补什么证据、什么时候再评；返工期间维持已批准的投入，不追加 |
| 停止 | 达不到门槛，或者碰到了停止标准 | 原因、已有产物和经验放哪里、释放的人何时回到资源分配表（有组合层时）或回到成员台账的排期；难以撤回的，另记一份 ADR |

**判的时候**：
- 只看接下来再投入值不值，已经花掉的不是继续的理由。
- 对照表逐项写：门槛（上次写的）、现有证据、是否达到。证据缺的一项写 `空缺`，不写达到。本阶段原本要验证的假设，逐条写验证结果，以及当初说好假设不成立时要怎么办。
- 涉及人身安全、合规或业务连续性的门槛没达到的，只能判返工或停止。
- 过了评审，不等于后面的风险都没了。RAID 日志照常复核。
- 任何结论（包括暂停、返工）只要改到里程碑、范围或已放行 PRD，都按第 4 节走变更请求，由本次拍板人一并批准。

`阶段评审-<项目或成员>-<序号>.md`：单个项目放 `pm/` 根目录，组合里的成员放 `pm/组合/`。

```markdown
# 阶段评审：<项目或成员> · 第 <n> 次 · <YYYY-MM-DD>
```
