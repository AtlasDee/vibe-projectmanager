# 第 7 段：建工单

> 由 SKILL.md 第 1 节指向。改编自 agnostic-planning-skills 的 `plan-tickets` 建单就绪检查与 `github-issue`（只在明确授权时写工单、不假设字段与凭证）。
> ⚠️ 本段是链路里写外部系统最多的一段（工单系统）。授权规则见 SKILL.md 第 6 节「外部写操作要授权」：每一次建单都要用户在**当前这条消息**里明确同意。

## 1 授权与就绪检查

动手前逐项确认，缺一项就停下问：

| # | 检查 | 说明 |
|---|---|---|
| 1 | 用户在当前这条消息里明确说了「建」 | 「帮我拆一下工单」只是草稿请求，不算授权；之前消息里的同意不延续到这一次 |
| 2 | 建到哪里 | 工单系统（GitHub Issues / Jira / 飞书项目等）、项目或看板名称，由用户给出，不从文档里推断 |
| 3 | 建哪些、建几条 | 默认按台账排名，只建用户点名的范围（如排名前 8、Sprint 3 选中的） |
| 4 | 字段 | 必填字段名、类型字段、标签规范，从工单系统的元数据或项目已有工单里查，不猜 |
| 5 | 凭证与工具 | 命令行工具已登录或接口凭证已配置在项目外；凭证不写进任何产物 |
| 6 | 门禁 | 所建任务所属的需求处于放行状态，且 PRD md5 比对一致（SKILL.md 第 2 节第 1、2 条）；非 PRD 来源的写明了具体来源 |

## 2 执行

1. **先建一条试**：字段、Sprint 行为、默认状态不确定时，先建一条给用户看，确认无误再批量建。
2. **不设状态**：新工单用工单系统的默认初始状态，不在创建时直接设成进行中等。
3. **不编字段值**：负责人、Sprint、优先级、标签，项目没规定或用户没给就留空。
4. **工单内容**取自台账与任务详情（写进工单的文字按 SKILL.md 第 6 节，不用直角引号）：

```markdown
标题：<任务标题>

背景：<一两句，引 PRD 章节号或非 PRD 来源>
要做什么：<任务详情里的描述>
验收标准：
- [ ] ……（逐条转写台账，含 🔵 标记）
依赖：<依赖任务对应的工单号；尚未建单的写任务编号>
估算：<台账估算 + 置信度>（项目有估算字段时填字段）
来源：<PRD 名称 · 章节号> · 台账 T-xx
```

5. 按依赖顺序建，建好后把真实工单号回填台账「工单号」列，并补全工单间的依赖链接。
6. 失败的单逐条记下原因，不重复提交同一条。

## 3 各系统要点

| 系统 | 要点 |
|---|---|
| GitHub Issues | 需要 `gh` 命令行已登录、当前目录有 GitHub 远程；先查仓库有没有 issue 模板、Projects、里程碑、已有的标签规范。有模板按模板填；仓库已有类型标签规范的按规范打，没有就不打 |
| Jira | 先查项目的创建元数据（必填字段、问题类型），故事点字段名因实例而异，查到再填 |
| 飞书项目 / 其他 | 走该系统的开放接口或用户指定的工具；字段规则同上，查到再填 |

> 状态变更（开始做、提测、关闭）也是写操作，同样逐次授权；第 9 段状态汇报只**读**工单状态，不顺手改。

## 4 产出

- 建成清单：`任务 ID / 工单号 / 链接 / 结果`；失败项单列原因。
- 台账「工单号」列已回填。

## 5 自检

- [ ] 授权来自用户在当前这条消息里的原话，目标系统与范围由用户给出
- [ ] 字段名、标签规范从元数据或已有工单查到，没有猜
- [ ] 不确定时先建了一条试
- [ ] 创建时没设状态，没编负责人、Sprint、优先级、标签
- [ ] 工单号已回填台账，没有把草稿当成已建
