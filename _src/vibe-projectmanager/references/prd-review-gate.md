# 第 2 段：评审 PRD 与门禁

> 由 SKILL.md 第 1、2 节指向。目标：判断这份 PRD 能不能交给拆任务和估算，不判断这个想法好不好。
> 门禁的判定、轮次上限、变更评审、豁免这些铁律写在 SKILL.md 第 2 节，本文件只写评审怎么做、记录怎么写。
> 改编自 agnostic-planning-skills 的 `review-prd`（评审清单、严重度、结论）与 `judgment-gate`（窄问题、独立评审、存疑与矛盾、轮次上限、升级）。

## 1 评审前：冻结

1. 确认被评审的是**哪一版**，记下版本 md5。冻结时和第 3～8 段开工前比对时，**用同一种算法、同一条命令**。哈希口径：按 UTF-8 读入，换行统一为 `\n`，去掉首尾空白后，对 UTF-8 字节算 md5。
   - **本地 md**（算法记为 本地整文件）：对整个文件按上述口径算。
     ```bash
     python -X utf8 -c "import sys,hashlib;t=open(sys.argv[1],encoding='utf-8').read();print(hashlib.md5(t.strip().encode('utf-8')).hexdigest())" <PRD 文件>
     ```
   - **云文档**（算法记为 云文档正文）：先用 Lark_Bot 导出，参数写死，不加别的选项：
     ```bash
     C:\Work\Lark_Bot\.venv\Scripts\python.exe -X utf8 C:\Work\Lark_Bot\export_docx_to_md.py <链接> --no-comments --no-images --out=pm/<需求简称>/_门禁导出
     ```
     `--no-comments` 是因为脚本默认把评论整节写进文件，有人加一条评论 md5 就会变；`--no-images` 让每张图都输出成同一个占位，避免下载失败或文件名前缀不同带来噪声。
     导出文件的文件头结构固定：`# 标题`、空行、`> 来源：` 行（只有用链接导出时才有）、`> docx token：` 行、`> 导出方式：` 行、空行。**只剥掉这个文件头**（从开头到 `> 导出方式：` 行后面那个空行为止），其余一字不跳：正文里的高亮块、引用块同样以 `>` 开头，开篇摘要就是高亮块，不能跳。
     ```bash
     python -X utf8 -c "import sys,hashlib;t=open(sys.argv[1],encoding='utf-8').read();i=t.index('\n> 导出方式：');b=t[t.index('\n',i+1)+1:];print(hashlib.md5(b.strip().encode('utf-8')).hexdigest())" <导出文件>
     ```
     导出时如果提示内嵌电子表格读取失败，重导一次再算，不拿带失败占位的文件定版本。
     **md5 覆盖不到的**：图片换了（同一位置换截图）、画板改了（只导出成占位），md5 都不变。云文档修订号拿得到就一并记下，评审时口头确认图片、画板有没有动。
   - **留档**：冻结用的导出文件（或本地 PRD 的副本）改名为 `<md5 前 8 位>.md`，留在 `pm/<需求简称>/_门禁导出/`。之后比对不一致时，先和留档 diff 一下，分清是正文实质改动，还是导出噪声（如被引用的文档改了名、表格读取失败）：属于噪声的，在门禁记录里注明原因并按新导出重记 md5，不当作 PRD 改动。
   - 评审时要读评论的，另导一份带评论的到别的目录（`--out` 不同，否则同名文件会互相覆盖），不用它算 md5。
   记下所用算法（本地整文件 / 云文档正文）。评审过程中 PRD 不改。
2. 写明本次要做的决定：这份 PRD 能否进入拆任务。
3. 能拿到就一并读入（不是必需）：BRD、[vibe-designing-intake] 澄清清单的答复、[vibe-designing-testcase] 的可验证性体检报告、[vibe-designing-acceptance] 的原型验收报告。已有结论的问题直接引用，不重复评。
4. 复评时（第 2、3 轮）先读本周期上一轮的 `评审报告-周期<c>-第<n>轮.md`，拿到上一轮阻塞项的明细。新周期的第 1 轮先读上一周期最后一轮的报告和门禁记录里的用户裁定，然后**全文评审**：重开评审通常意味着 PRD 改动面大，只看改动处不够。

## 2 评审清单

每一问都要能用「是 / 否 + 证据」回答。「这份 PRD 好不好」不是一个问题。

| 维度 | 问题 |
|---|---|
| 完整 | 需求目标有没有可度量的成功指标（口径 + 基线 + 目标值）？ |
| 完整 | 功能清单里的每一项，在功能详细说明里都有对应模块吗？ |
| 完整 | 每个有状态的对象，都有状态-操作矩阵或等价说明吗？ |
| 可验证 | 每条规则能否写成一条通过 / 不通过的用例？（有 testcase 体检报告时直接引用） |
| 可验证 | 字段表的必填、长度、值域、报错文案写全了吗？ |
| 清楚 | 有没有未定义的术语（名词解释里查不到）？ |
| 清楚 | 有没有「适当」「尽量」「等」「支持多种」这类说不清边界的词？ |
| 清楚 | 前后有没有矛盾（同一规则两处写法不同、表格列名不一致）？ |
| 可行 | 依赖的外部系统、接口、数据源都点名了吗？有没有 🔵 卡在主流程上？ |
| 可行 | 有没有明显需要先做技术预研（spike）才能估算的地方？ |
| 边界 | 失败、空态、异常、权限不足、并发等场景有没有写？ |
| 边界 | 涉及存量数据或旧版本时，迁移与兼容写了吗？ |

> 范围按 SKILL.md 第 6 节「不写不做什么」判断，不因缺 Out-of-Scope 判缺失。
> 后台 / 中台需求再加两问：权限节点表是否覆盖所有操作；操作日志表是否覆盖所有写操作。

## 3 独立评审

**两路评审**，用同一份清单、同一个冻结版本：

- **第一路**：派一个**没参与写这份 PRD**的子代理冷读，只给它冻结版 PRD 和上面的清单，不给作者的解释。
- **第二路**：主会话再过一遍，换一种问法（例如从开发的视角：「拿到这份 PRD，我能不能开始估算」）。
- **没有子代理可用时**：主会话按两种问法各过一遍（先逐条清单，再开发视角），两遍之间不回看第一遍的结论；门禁记录的「评审方式」照实写。

每一路都要**对清单的每一问给出判断和置信度**（高 / 中 / 低）。缺答的问题不算评过：让那一路补齐，不拿半份结果合并。

**合并**：

| 情况 | 判定标准 | 处理 |
|---|---|---|
| 确认 | 两路都认定是问题 | 按严重度归类 |
| 存疑 | 一路认定是问题，另一路**没有提到** | 单列存疑，不自动当阻塞项；放行前请用户逐条处置 |
| 矛盾 | 一路认定是问题，另一路对同一处**明确判定不是问题并给出证据** | 不取平均，列为升级项 |

> 「存疑」管的是**有没有这个问题**；下面第 4 节「拿不准的归阻塞项」管的是**已确认的问题有多严重**。两者不是一回事。

## 4 严重度

| 级别 | 判断标准 | 门禁影响 |
|---|---|---|
| ⛔ 阻塞项 | 会改变做出来的东西，或让拆任务、估算无法进行：主流程缺规则、状态流转不全、前后矛盾、**卡在主流程上或让估算无法进行的 🔵** | 有一条就不放行 |
| ⚠️ 小问题 | 不改变做出来的东西：措辞、格式、次要字段的提示文案；**不卡主流程、不影响估算的 🔵** | 不阻塞，放行时列进遗留项；会影响排期的，第 5 段登记进 RAID 日志：已有暂定口径的 🔵 记为假设（写明暂定值），没有暂定口径的记为风险（模式：需求不明） |
| 📝 备注 | 写得好的地方、给作者的提醒 | 无 |

已确认的问题，拿不准是阻塞项还是小问题的，归阻塞项。

## 5 结论

| 结论 | 条件 | 下一步 |
|---|---|---|
| ✅ 通过 | 0 阻塞项 | 请用户逐条处置存疑项（认定为阻塞项的，结论改为不通过）；再请用户确认放行，确认后写入门禁记录，进第 3 段 |
| ⛔ 不通过 | 有阻塞项 | 把阻塞项交给用户。是否修改、由谁修改由用户决定（可交 [vibe-designing] 对应分件）；修改后重新冻结，进入下一轮复评 |
| ⚠️ 升级 | 第 3 轮仍有阻塞项，或有矛盾项 | 交用户裁定：放行（记 `用户裁定放行`）、继续修改（记 `用户裁定重开评审`，进入下一个周期，轮次从 1 重计）、或搁置；裁定有长期影响的，记一份 ADR |

轮次上限见 SKILL.md 第 2 节第 5 条。门禁只有放行与未放行两种出口，不设「有条件通过」：PRD 还要改的话，在它上面估算和排期都会返工。（[vibe-designing-acceptance] 的原型验收和 `governance.md` 的发布关卡设有条件结论，场景不同。）

**复评只看改动**：同一周期内的第 2、3 轮，只核对上一轮的阻塞项是否修好，以及修改处有没有引入新问题，不重新全文评审。新周期的第 1 轮按第 1 节第 4 步全文评审。

## 6 产出

### 6.1 `评审报告-周期<c>-第<n>轮.md`

存在需求目录下，复评和换会话时都靠它（周期号从 1 起，用户裁定重开评审时加 1）：

- 评审对象与版本（同门禁记录）；
- 结论；
- 阻塞项表：`# / 章节 / 问题 / 证据 / 建议改法`；
- 小问题表（同列，🔵 类的注明）；
- 存疑表：`# / 章节 / 哪一路提出 / 问题 / 证据 / 用户处置`；
- 矛盾表（如有）：两路各自的判断与证据；
- 按严重度计数；写得好的地方一两条。

证据里涉及账号、手机号、内部链接等敏感信息的，脱敏后再写。对话里给出摘要即可。

### 6.2 `门禁记录.md`

每轮追加一节，最新的一节放最下面。模板（写进文件的文字按 SKILL.md 第 6 节，不用直角引号）：

```markdown
## 周期 <c> · 第 <n> 轮 · <YYYY-MM-DD>

- 评审对象：<PRD 路径或云文档名>
- 版本：md5 <值>（算法：本地整文件 / 云文档正文）· 修订号 <值或 无>
- 评审方式：<子代理冷读 + 主会话复核 / 主会话两种问法各一遍>
- 结论：通过 / 不通过 / 升级
- 阻塞项：<n> 条，明细见 评审报告-周期<c>-第<n>轮.md
- 存疑项：<n> 条，用户处置：<逐条结果>
- 遗留项（小问题）：<n> 条，待第 5 段登记 RAID（登记后回填编号：<R-xx / A-xx>）
- 门禁：放行 / 未放行 / 用户裁定放行 / 用户裁定重开评审 / 用户豁免（原因：……）
- 确认人：<用户在对话中的原话摘要>
```

变更评审追加一节：

```markdown
## 变更评审 · CR-<编号> · 第 <n> 次 · <YYYY-MM-DD>

- 改动范围：<PRD 章节号>
- 新版本：md5 <值>（算法：本地整文件 / 云文档正文）· 修订号 <值或 无>
- 评审结论：通过 / 不通过 / 升级（只评改动部分），明细见 评审报告-CR-<编号>-第<n>次.md
- 受影响任务：<T-xx …>，CR 批准时已在台账估算列标 待重估
- 门禁：放行 / 未放行 / 用户裁定放行 / 用户裁定继续修改 / 撤回恢复放行（恢复到：<上一个放行节的标题>）
- 确认人：<用户原话摘要>
```

豁免追加一节：

```markdown
## 豁免 · <YYYY-MM-DD>

- 评审对象：<PRD 路径或云文档名>
- 版本：md5 <值>（算法：本地整文件 / 云文档正文）· 修订号 <值或 无>
- 原因：<用户给出的原因>
- 门禁：用户豁免
- RAID：<登记的 R-xx（PRD 未评审）>
- 确认人：<用户原话摘要>
```

### 6.3 变更评审怎么做

- 按第 3 节两路评审，**只评改动部分**及其直接影响到的规则；清单只问与改动相关的条目。
- 结论与严重度按第 4、5 节判；报告写成 `评审报告-CR-<编号>-第<n>次.md`。
- 不通过：交用户决定怎么改，改后同一个 CR 再评一次；**同一个 CR 第 2 次仍不通过，结论为升级**，交用户裁定：
  - **放行**：记 `用户裁定放行`；
  - **继续修改**：记 `用户裁定继续修改`，改后同一个 CR 再评；此后每次仍不通过都直接交用户裁定，不自动加轮；
  - **撤回 CR**（搁置同样按撤回处理）：PRD 已经改过的，要回退到上一个放行版本。按第 1 节重算 md5，与上一个放行节记下的 md5 一致后，追加一节，「门禁」栏记 `撤回恢复放行` 并写明恢复到哪一节。PRD 没回退之前，这一节的「门禁」栏为 `未放行`，第 3～8 段照常被拦。
- 受影响任务在 **CR 批准时**就在台账估算列标 `待重估`（`governance.md` 第 4 节）；变更评审放行后，把台账表头的已放行版本 md5 更新为新版本。CR 撤回的，去掉这些 `待重估` 标记，恢复原估算。

## 7 自检

- [ ] 被评审的版本已按第 1 节的命令算出 md5，记了所用算法；云文档只剥掉固定文件头，正文的 `>` 行没跳；导出文件已留档；评审中 PRD 没改
- [ ] 评审报告文件名和门禁记录节标题带了周期号；豁免、变更评审也各记了 md5
- [ ] 每条问题都引了章节号，没有提替代方案（不可行的除外）
- [ ] 两路评审对每一问都有判断和置信度；冷读那一路没看到作者的解释
- [ ] 存疑与矛盾按定义区分；存疑项已请用户处置
- [ ] 🔵 按是否卡主流程、是否影响估算分了级
- [ ] 结论为通过时，放行经用户确认；评审报告与门禁记录已写入文件
- [ ] 没有自行改 PRD；轮次未超过上限
